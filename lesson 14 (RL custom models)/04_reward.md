# Проектирование награды

## Цель

Собрать награду не одной строкой, а реестром именованных членов, и для каждого члена уметь предъявить доказательство:
таблицу ставки в награде за секунду, вердикт «градиент есть / нет градиента / градиент обратный» и долю члена в сумме.
Проверки делаются на синтетическом состоянии **до** обучения, а не по кривой в TensorBoard после. Главный тезис
главы: **вес члена — последнее, что нужно крутить.** Почти все дорогие ошибки этого урока — ошибки не веса, а формы:
член платил за другое, платил постоянную величину, платил недостижимый порог или затирал соседей.

## 1. Три класса награды на трёх треках

| Трек | Что оплачивается | Награда — функция чего | Среда |
|---|---|---|---|
| A — парковка | расстояние и курс до места | текущей позы | [car_env.py](track_a_car/car_env.py) |
| B — ходьба | совпадение скорости с командой | позы и команды | [walk_env.py](track_b_walk/walk_env.py) |
| C — облёт | **доля уже отснятой поверхности** | позы **и истории эпизода** | [scan_env.py](track_c_drone/scan_env.py) |

A и B устроены одинаково: есть целевое значение, есть текущее, платим за близость. Такая награда стационарна внутри
эпизода — одна и та же поза всегда стоит одинаково. C принципиально иной, [scan_env.py:7-12](track_c_drone/scan_env.py):

```
      * она зависит от ИСТОРИИ (ценность точки пространства зависит от того,
        отснята ли уже соответствующая ячейка) — то есть не марковская по позе;
      * поэтому карта покрытия ОБЯЗАНА лежать в наблюдении, иначе награда
        физически ненаблюдаема и штраф превращается в шум;
      * она субмодулярна: отдача убывает, и без штрафа времени задача
        вырождается в «когда-нибудь долети».
```

Три следствия, каждое видно в коде или в замере.

1. **Карта идёт в наблюдение.** `n_obs = 4 + 3 + 2 + 1 + n_rays + 1 + 5*n_band + 4` ([scan_env.py:247](track_c_drone/scan_env.py))
   = 60 чисел, из них 1 — доля покрытия и 30 — локальная карта; без этих 31 канала награда была бы ненаблюдаемой.
2. **Нужна разведка, а не удержание в хорошей точке.** Замер отгружаемых политик
   (`cd track_c_drone && python evaluate.py --hover policies/hover --scan policies/scan --episodes 20`,
   среда с `cov_target = 1.01`, эпизод идёт все 1500 шагов): нулевое действие — покрытие **0.0120** и ноль аварий;
   случайная политика — **0.1307** и авария в 100 % эпизодов; скриптовый облёт — 0.9906, но **1116** шагов до порога
   0.85; обученная PPO — **0.9943** и **361** шаг, в 3.1 раза быстрее скрипта. Потолок берут обе, различаются они
   временем.
3. **Штраф времени обязателен**: из-за субмодулярности «когда-нибудь долечу» даёт почти то же покрытие. Задачей на
   время её делает `time` (`-0.01` за шаг, [scan_env.py:141](track_c_drone/scan_env.py)), а против обратного
   вырождения — «прижаться к поверхности, раз ячейка засчитывается с 2.5 м» — стоит `near` = `-1.0*max(0, 1.35 - d)`.
   Соотношение весов проверяется критерием, а не подбором: скриптовый облёт обязан набрать положительную суммарную
   награду, идеальное висение — отрицательную.

## 2. Потенциальный шейпинг: строго, с gamma

Теорема Ng, Harada, Russell (1999): добавка вида `F(s, a, s') = gamma*Ф(s') - Ф(s)` не меняет множество оптимальных
политик. Доказательство — телескопирование, и рядом та же выкладка без `gamma`:

```
с gamma:   SUM_t gamma^t*F_t = SUM_t [gamma^(t+1)*Ф(s_(t+1)) - gamma^t*Ф(s_t)] = -Ф(s_0)
без gamma: SUM_t gamma^t*[Ф(s_(t+1)) - Ф(s_t)] - SUM_t gamma^t*F_t = (1-gamma)*SUM_t gamma^t*Ф(s_(t+1))
```

В первой строке правая часть **не зависит от политики** — это константа, определяемая стартом (последний член
обнуляется, если положить Ф терминального состояния нулём), а прибавление константы не меняет argmax. Во второй
строке лишнее слагаемое на шаг равно `(1-gamma)*Ф(s')`; потенциал парковки неположителен по построению
(`Ф = -(W_DIST*dist + heading_weight*|dyaw|)`), значит это **скрытый штраф за расстояние**. Замер старой версии
урока, писавшей `Ф(s') - Ф(s)` (04_lesson14_code.md §2.2, `p18_dense.py`, 40 эпизодов обученной политики):

```
sum of (1-gamma)*phi(s') over an episode: mean=-23.34  min=-37.87 max=-11.62
compare with: explicit time penalty = -5.21 | total shaping = +4.51 | success bonus = +100
```

**−23.3 за эпизод** — в 4.5 раза больше явного штрафа за время и 23 % от бонуса за парковку. Шейпинг перестал быть
шейпингом. Как сделано сейчас — [car_env.py:335](track_a_car/car_env.py), член `progress` реестра:

```python
                fn=lambda c: g * c["phi"] - c["phi_prev"],
```

`g = self.gamma` берётся из конструктора ([car_env.py:330](track_a_car/car_env.py)) и обязана совпадать с `gamma`
алгоритма — инвариантность доказана для одной и той же `gamma`; в среде это `GAMMA = 0.995`
([car_env.py:97](track_a_car/car_env.py)). Поле `why` этого члена (строки 338-343) содержит тот же разбор, что выше:
обоснование живёт в коде, а не в чьей-то памяти.

**Побочный эффект, который надо оплатить.** Корректный шейпинг платит неподвижной машине `(gamma-1)*Ф(s)`, а это
неотрицательно, потому что `Ф <= 0`. Арифметика на двух точках рабочего диапазона:

```
dist=0.30, dyaw=0.10 -> Ф = -(2*0.30 + (2/(0.5+0.30))*0.10) = -0.850 -> 0.005*0.850/0.05 = +0.085 /с
dist=2.50, dyaw=1.57 -> Ф = -(2*2.50 + (2/(0.5+2.50))*1.57) = -6.047 -> 0.005*6.047/0.05 = +0.605 /с
```

Оба числа совпадают с замером в [car_env.py:179-190](track_a_car/car_env.py), оттуда же последствие:

```
# При STEP_COST=0.02 (то есть 0.4 награды/с) пассивная политика получала
# ЗА ЭПИЗОД +2.738 шейпинга против -2.400 времени, итого +0.338:
# стоять на месте было ВЫГОДНО. STEP_COST=0.05 -> 1.0 награды/с перекрывает
# ставку неподвижности на всём рабочем диапазоне; пассивный возврат
# становится -3.26 за эпизод (перепроверено probe.py, проба 7).
```

Число **−3.26** — от той калибровки, на которой `STEP_COST` и выбирали; сегодня проба печатает **−4.892**
(`cd track_a_car && python probe.py`, проба 7; разброс по 8 эпизодам 0.223). Устойчив здесь знак, а не величина.

Правило: после каждого изменения потенциала пересчитайте ставку неподвижности и проверьте, что плата за время её
перекрывает.

## 3. Реестр членов: `Term` и `RewardRegistry`

Монолитная награда не отвечает на единственный вопрос, нужный при отладке: **кто сколько платит.** Реестр из
[rewards.py](rl_toolkit/rewards.py) хранит члены по именам, отдаёт вклады в `info["terms"]` и считает ставку в
секунду. Член — датакласс [rewards.py:131-158](rl_toolkit/rewards.py) с полями `name`, `fn`, `weight`, `unit`,
`why`, `gate`, `threshold`; значение = `weight * fn(ctx) * gate(ctx)`, ставка = `value / ctx.dt`.

**Почему `why` обязателен.** Формально это строка документации, практически — фильтр на входе. Правило курса: член,
для которого нельзя написать `why`, не нужен. Масштаб: в боевой среде шагохода **24** члена награды
([walk_env.py:6](track_b_walk/walk_env.py)) — в `info` одного прогона их видно 23, один событийный за эпизод
не сработал (замер приёмки, 11_acceptance.md §L8); в учебной [walk_env.py](track_b_walk/walk_env.py) — шесть плюс
терминальное событие падения.
Второе назначение: `why` печатается в отчёте, то есть обоснование веса лежит рядом с числом. Третье: `why` фиксирует,
**за что** член платит, и это утверждение проверяется замером — `r_stride` боевой платформы честно набирал
21.9 награды/с, но мерил смещение стопы в СК корпуса, а оно для любой периодической походки тождественно ноль, то
есть платил за апериодичность (06_pitfalls.md §A1).

**Почему вклад считается за секунду, а не за шаг** ([rewards.py:9-12](rl_toolkit/rewards.py)): «Веса калибруются в
единицах награда/с: только так сравнимы члены, начисляемые на каждом шаге, и члены, начисляемые по событию (посадка
стопы, пересечение порога)». Шаговый член даёт за секунду `value/dt`, событийный с частотой `f` — `плата*f`; за шаг
они несравнимы (у второго на большинстве шагов ноль), а конкурируют интегралом за эпизод. Отсюда договорённость
([rewards.py:53-58](rl_toolkit/rewards.py)): событийный член записывается как `плата * f * dt`, и именно эта запись
делает видимой ошибку формы из §4. Плюс: смена `dt` при учёте «за шаг» молча меняет все веса, при учёте «за
секунду» — не меняет ничего.

Фактический вывод `python -m rl_toolkit.rewards`, пункт 2 самопроверки:

```
2. Душитель: ставки -105.5/с и +84.5/с (числа из walk_env_r4.py:259-264)
   вклад членов награды: 50 шагов, dt=0.02 с, 1.000 с, сумма -16.000 (-16.000/с, модуль 195.000/с)
   член             |   награда/с |   доля | знак | ненулевых | единица  | зачем
   -----------------------------------------------------------------------------
   p_new            |    -105.500 |  54.1% |    - |        50 | доля     | новый штраф с весом 0.5  <-- >40 % |суммы|, кандидат в душители
   r_lin            |      84.500 |  43.3% |    + |        50 | доля     | слежение за командой  <-- >40 % |суммы|, кандидат в душители
   r_small          |       5.000 |   2.6% |    + |        50 | доля     | мелкий бонус
   доля душителя 54.1 % от |суммы| — помечен верно.
```

Пункт 3 того же вывода — трек B: абсолютное ядро `exp(-8*err^2)` платит **неподвижной** машине 92.31 % награды
слежения при команде 0.10 м/с и 27.80 % при 0.40 м/с, а относительное с `sigma = max(0.35*|cmd|, 0.07)`
([walk_env.py:149](track_b_walk/walk_env.py)) — 1.69 % в худшей точке и 0.00 % дальше. Это арифметика до запуска; на
аттракторе «стоять выгоднее» соседняя ветка проекта сожгла пять версий подряд (06_pitfalls.md §A4).

## 4. Форма платы: почему подъём веса 8 → 12 ничего не изменил

Симптом (06_pitfalls.md §A2): робот семенит, шаг 58 мм. В награде есть член, который платит именно за длину шага, вес
ему подняли в полтора раза на отметке 70 млн шагов — шаг не изменился.

Разбор. Плата вида `min(L/L_cap, 1)` начисляется за каждую посадку. При каденсе `f` посадок на ногу в секунду и двух
ногах событий `2f` в секунду; в установившейся ходьбе скорость задана командой, то есть `L*f = v`. Отсюда ставка:

```
rate = 2*f*W*L/L_cap = 2*W*v/L_cap
```

**Длина шага сократилась.** Ставка не зависит от величины, которой член назван, и умножение на любой вес умножает
ноль на константу. Замер платформы: `L = 0.058 м -> 11.33/с`, `L = 0.300 м -> 11.16/с`. Шаг впятеро длиннее даёт
ставку на 1.5 % **хуже** — градиент не просто нулевой, он слегка отрицательный. Тот же расчёт воспроизводится
командой `python -m rl_toolkit.diagnostics` на своих числах (`W = 8`, `v = 0.25`, `L_cap = 0.3`, `dt = 0.02`):

```
свип члена 'r_stride_cap' по оси 'L, м' (dt=0.02 с, вес 8)
  L, м |  сырое | награда/с
-------+--------+----------
0.0580 | 0.0333 |   13.3333
0.3000 | 0.0333 |   13.3333
!! ВЕРДИКТ: нет градиента (размах=3.553e-15, относительный размах=2.665e-16, ...)
   аналитика: 2*W*v/L_cap = 2*8.0*0.25/0.3 = 13.3333/с при ЛЮБОЙ длине шага

   тот же член с весом 12: ставка 20.0000/с при L=0.058 и 20.0000/с при L=0.300 — вердикт: нет градиента
   вывод: вес умножил ноль на 1.5 и получил ноль (06_pitfalls.md §A2).
```

За потолком `L_cap` становится хуже: при `L = 0.45` ставка падает до 8.89/с и вердикт меняется на «градиент
ОБРАТНЫЙ». **Лечение — смещение от порога вместо доли от потолка.** Ключ в знаке, а не в величине: плата пишется
как `gain = min(L, L_max) - L_0`, и посадка короче порога становится **чистым штрафом**, а не «менее выгодной
наградой». Тот же свип после правки:

```
свип члена 'r_stride_offset' по оси 'L, м' (dt=0.02 с, вес 8)
  L, м |   сырое | награда/с
-------+---------+----------
0.0580 | -0.0055 |   -2.2069
0.1000 |  0.0010 |    0.4000
0.4000 |  0.0078 |    3.1000
0.4500 |  0.0069 |    2.7556
OK ВЕРДИКТ: градиент есть (размах=5.307, ...); внутренний максимум при L, м = 0.4 (3.1000/с)
    есть СМЕНА ЗНАКА — плохое поведение становится чистым штрафом
```

Потолок `L_max` обязателен: без него член линеен по `1/f` и тянет каденс в ноль. Последствие правки на платформе:
походка 5.25 Гц / 0.058 м стала получать **−14.0/с** вместо прежних **+22.8/с**; после прогона шаг вырос
11.2 → 34.1 см, каденс упал 5.1 → 2.0 Гц, слежение выросло 78 % → 91.7 % (06_pitfalls.md §A2). Правило: перед
запуском выведите ставку в единицу времени как функцию целевой величины и продифференцируйте; «поднять вес» —
лечение только там, где градиент есть, но слаб.

## 5. Конфликт членов: длинный шаг удвоил раскачку по крену

Победа предыдущего пункта обернулась новой жалобой заказчика: робот трясёт грузом. Замер `_probe_payload.py` при
команде 0.4 м/с (06_pitfalls.md §B14):

| величина | до правки шага (78.5M) | после (86.5M) | |
|---|---|---|---|
| крен | 1.87° | **3.77°** | вдвое хуже |
| скорость крена, rms | 40 °/с | 46 °/с | хуже |
| боковое ускорение, rms | 0.401 g | **0.321 g** | **лучше** |

Это не побочный баг, а физика: у машины точечная стопа, и чтобы шагнуть длиннее, центр масс обязан сильнее уходить
на опорную ногу; требования «длинный шаг» и «спокойный груз» противоречат напрямую. Обратите внимание на третью
строку: замер **разошёлся по компонентам** — тряска уменьшилась, раскачка удвоилась; одно скалярное «стало хуже» тут
было бы неправдой.

Вывод: **давить надо не на амплитуду, а на производные.** Увод центра масс нужен физически, поэтому штрафуются
скорость крена и боковое ускорение в точке груза, а не сам наклон. Плюс крен и тангаж разделяются: в боевой среде
`W_ROLL = 40.0`, `W_PITCH = 4.0` ([_reference_walk_env_r4.py:327](track_b_walk/_reference_walk_env_r4.py)) —
вдесятеро. В учебной среде веса симметричны, и это сознательная правка с обоснованием
([walk_env.py:112-114](track_b_walk/walk_env.py)):

```
# ПРАВКА 1. В боевой среде крен наказан в 10 раз дороже тангажа
# (W_ROLL = 40.0, :720) — потому что наверху корпуса стоит ГРУЗ, и качает
# его именно крен. В курсе груза нет, поэтому вес симметричный
```

Асимметрия весов — функция полезной нагрузки, а не фольклор. Что переносится без изменений — квадратичность **от
нуля**: свободная полоса 20° вокруг вертикали занулила градиент у вертикали, и 24 млн шагов ушли в аттрактор
«медленно валиться вбок». Конфликты выписываются заранее, с правилом разрешения: «`p_alat` и вес крена тянут к
КОРОТКОМУ шагу… Если шаг просядет ниже ~15 см — снижать W_ALAT, а НЕ W_STRIDE» (06_pitfalls.md §B14).

## 6. Член-душитель: доля выше 40 %

Вес сам по себе ничего не значит — значение имеет доля члена в сумме. Порог курса: член, забирающий больше ~40 %
модуля суммы за секунду, — кандидат на пересмотр; `report()` помечает такой член строкой
«`<-- >40 % |суммы|, кандидат в душители`» ([rewards.py:400](rl_toolkit/rewards.py)). Числа, из которых взят порог
([rewards.py:16-25](rl_toolkit/rewards.py)): при весе 0.5 новый штраф давал **−105.5/с** против `r_lin` **+84.5/с** и
задавил всё остальное — полная награда падала с ~700 до 2.45/с, при весе 0.15 это ~32/с. Другой случай: при весе 2.0
новый блок съедал **48 %** награды заднего хода, и вес снижен до 1.5, иначе политика рискует выучить «назад лучше не
ходить». Душитель не ломает обучение ошибкой — он **отключает режим**. Живой отчёт печатает любая среда урока;
пассивный эпизод трека B (`python walk_env.py`, действие 0, машина падает через 1.06 с):

```
вклад членов награды: 53 шагов, dt=0.02 с, 1.060 с, сумма -19.769 (-18.650/с, модуль 119.800/с)
член             |   награда/с |   доля | знак | ненулевых | единица
p_fall           |     -47.170 |  39.4% |    - |         1 | событие
r_lin            |      31.063 |  25.9% |    + |        53 | доля
r_height         |      14.512 |  12.1% |    + |        53 | доля
p_tilt           |     -13.948 |  11.6% |    - |        53 | g^2
p_idle           |      -8.107 |   6.8% |    - |        47 | доля
```

Читается так: терминальный штраф падения даёт 39.4 % модуля, потому что эпизод короткий — один платёж −50 размазался
на 1.06 с; на здоровой ходьбе эта доля упадёт на порядок. Отсюда оговорка: **долю смотрят на обученной политике.**
В пробе 8.6 трека A на случайной политике ненулевые только `time` (−1.0000/с, доля 0.7195) и `progress` (+0.3898/с,
доля 0.2805) — их доли по определению делят единицу, и пометка там ожидаема.

## 7. Терминальные награды и обрыв эпизода

**Присваивание вместо прибавления.** Старая версия писала `reward = -30.0` вместо `reward += -30.0`
(04_lesson14_code.md §2.5): шаг, на котором агент заработал +65 лестницы бонусов и +100 за парковку и коснулся
соседа, платит ровно −30.

```
step() at (x=0.29, y=-0.46, yaw=-0.6) with _hold=7:
  reward=-30.0  terminated=True  info={'success': True, 'collision': True}
```

Возврат «почти припарковался, но задел соседа» равен возврату «влетел в стену на пятом шаге»: критик не различает
исходы. В реестре такая ошибка невозможна — `RewardRegistry.__call__` складывает вклады ([rewards.py:223-236](rl_toolkit/rewards.py)).

**Взаимоисключающие исходы разводятся порядком веток**, [car_env.py:503-507](track_a_car/car_env.py):

```python
        # ПОРЯДОК ВЕТОК — это и есть починка блокера Б3 (§3.3):
        # неудачные исходы проверяются ПЕРВЫМИ и исключают успех на том же шаге.
        success = False
        terminated = False
        if collision or oob or tipped:
```

Старые ворота успеха пересекались с множеством «столкновение» на **13.9 %** поз (перебор 6174 поз,
04_lesson14_code.md §3.3), и метрика считала такой шаг успехом. Рядом — правило про необратимость: член `tipped`
([car_env.py:408-420](track_a_car/car_env.py)) существует потому, что пока эпизод не обрывался, машина лежала вверх
дном оставшиеся 5 с из 6.

**Терминальный бонус считается в дисконтированных единицах.** Поле `why` члена `park`
([car_env.py:383-386](track_a_car/car_env.py)): «При dt=0.05 и gamma=0.995 бонус, полученный на шаге 60, стоит в
дисконтированной цели 100*0.995^60 = 74.0. У старой версии (100 Гц, gamma=0.99, медианный успех на шаге 460) тот же
бонус стоил 100*0.99^460 = 0.98». Написать в награде можно любое число; критик видит его помноженным на `gamma^t`.

## 8. Антипаттерны

**Reward hacking через порог засчёта.** Любой детектор события — дверь: агент будет держаться прямо под порогом.
Боевой случай: `L_STRIDE_0` стоял константой 0.12 м, а достижимый шаг равен `v/каденс` и при 0.25 м/с и 2.3 Гц
составляет 10.9 см. Порог недостижим, штраф платится всегда, и единственный способ уйти от него — не регистрировать
посадку вообще, свалив работу на одну ногу. Это и есть хромота: шаг Л/П 16.0 / 11.4 см, потеряно контактов
20 % / 5 % (06_pitfalls.md §A7). Ловится до обучения, `python -m rl_toolkit.diagnostics`:

```
4. ДОСТИЖИМОСТЬ ПОРОГА: константный порог против физики
   при v=0.25 м/с и каденсе 2.3 Гц достижимый шаг = 10.9 см
   !! ВЕРДИКТ: порог НЕДОСТИЖИМ (порог=0.12, достижимо max=0.1087, запас=-0.0113)
       порог 0.12 выше максимума достижимого 0.1087 (90.6 % порога) — штраф платится
       при ЛЮБОМ поведении, и политика будет искать не улучшение, а лазейку.
```

При `v = 0.60` м/с и каденсе 1.7 Гц достижимый шаг 35.3 см, и та же проба даёт «порог достижим»: лечение —
порог, пропорциональный команде. Обобщение: **недостижимый порог превращается в постоянный оброк**, а постоянное
слагаемое градиента не несёт (§4) — зато несёт стимул уклониться от учёта.

**«Халява» в старте.** Трюк «каждый пятый эпизод начинается уже на месте» задуман, чтобы критик увидел награду за
удержание, не доезжая. Но в старой версии он давал ровно **164.92** награды за 8 шагов в 20 % эпизодов (разложение
`+15 +20 +30 +100 −0.08`, 04_lesson14_code.md §3.4), и кривая, которую строит колбэк по эпизодам, равна
`0.8*R_дорога + 0.2*164.92`: при честных 60 на дороге график показывает **81**. В уроке трюк выключен по умолчанию
([car_env.py:172](track_a_car/car_env.py), `IN_SPOT_START_PROB = 0.0`), включается только куррикулумом, а эпизоды
помечаются `info["curriculum"]` ([car_env.py:539](track_a_car/car_env.py)) и фильтруются из кривой. Правило: любой
стартовый трюк обязан быть помечен в `info` и исключён из отчётной метрики.

**Награда, которая почти не различает политики.** Первая версия среды трека C (сетка 12×4, поле зрения 140°, без
предела дальности осмотра) давала случайной политике **0.62** покрытия (07_track_c.md §3.2) — потолок брался даром.
Три правки (сетка 16×6, камера ±35°/±22°, засчитывать ячейку только с дистанции ≤ 2.5 м) опустили её до 0.13.
Приёмочный тест среды: случайная политика должна набирать заметно меньше целевого уровня (в ТЗ трека C — «< 0.20»).

   ставку неподвижности `(gamma-1)*Ф(s)/dt` на краях диапазона и сверьте с платой за время (§2).
